杰理芯片 USB 烧录流程拆解

从运行态软触发、开机硬件握手到 RAM Loader 与 Flash 读写全流程

折腾这套纯软件 USB 烧录并把它封装成 jieli-build 技能（Skill），初衷是为了让 AI 能够独立跑通“写代码 → 编译 → 烧录 → 验证”的闭环开发。只要在固件里加上 USB 升级响应接口，插USB数据线直接直连，AI 改完代码就能自己发命令把新固件刷进板子验证，不需要每次都人工去按下载器；

等后面有空再做一块电脑可控硬件下载器，就算 AI 写出了坏固件把板子刷成砖，也能自己调硬件在芯片上电复位阶段发握手信号救活，实现彻底的全自动闭环。

最初知道可以免烧录盒直刷，是在 Yandex 搜索方案时看到俄罗斯 USMI 论坛上有大佬用 Arduino 玩杰理芯片，提到可以直接通过 USB 触发烧录，顺着这条线索把资料翻了一遍，才彻底摸顺了杰理下载程序的流程。

本文的具体代码与数据均以我实际验证过的 AC701N 工程为例，其他型号按对应 SDK 和编译配置确认即可，软件触发的前提是目标固件已经实现并启用了对应入口。

1、烧录流程

杰理芯片烧录分为三个阶段，先通过某种路径让芯片进入 ROM 下载模式，接着把临时加载程序传进芯片 RAM 运行，最后由这个 RAM 程序完成 Flash 擦写。

flowchart TD
    A[先确认固件提供下载入口] --> B{入口已启用且应用能响应请求？}
    B -->|是| C[电脑发请求，应用切换到ROM下载模式]
    B -->|未提供或无响应| D[外置工具使杰理复位并发送启动握手]
    D --> E[杰理ROM识别握手并进入下载模式]
    C --> F[电脑识别杰理下载设备]
    E --> F
    F --> G[电脑上传临时程序到杰理RAM并调用]
    G --> H[临时程序执行查询和Flash读写]
    H --> I[电脑发送启动命令]
    I --> J[杰理启动Flash中的固件]

整个过程中涉及三段职责完全不同的程序：

程序名称 存放位置 负责的工作 断电后的状态
ROM 启动程序 芯片出厂固化的掩膜存储区 上电最先执行，负责正常引导或提供基础下载入口 永久保留
RAM 临时加载程序（Loader） 存放在电脑端，刷机时上传到芯片 RAM 初始化存储驱动，向电脑提供 Flash 查询、读取、擦除与写入命令 断电即失，每次刷机重新上传
Flash 启动程序（Bootloader） 随固件烧录进 Flash（如 uboot.boot） 正常开机时引导应用固件，衔接 SDK 的启动与升级流程 保存在 Flash 中，随烧录更新

板子平时正常开机走的是“ROM 启动程序 → Flash 启动程序 → 应用固件”这条路；而电脑刷机走的是“ROM 下载入口 → RAM 临时加载程序 → Flash 读写操作”这条路，大佬 kagaimiq 的文档对 UBOOT1.00 下载阶段的说明详细解释了这套分工。只要能让芯片重新跑一次出厂 ROM 并在开机瞬间拦住它进入下载模式，哪怕 Flash 里的原有程序全毁了也不影响重刷。

2、固件内下载入口

软件烧录的前提是正在运行的固件能听懂“切换到下载模式”的请求。板子能枚举出普通 USB 串口、声卡或 U 盘，不代表这个升级入口已经打开，不能直接拿电脑脚本去套所有固件。

接入这个入口只需要四步：

  1. 找到目标固件处理 USB 控制请求的回调函数，确认里面有没有处理 0xFC/0xFE 私有请求并调用下载切换函数。
  2. 确认这段代码真正参与了编译并被注册到 USB 分发链路里；如果没有，就按 SDK 的回调机制补上。
  3. 先用官方烧录器或现有的升级方式，把带有这个入口的固件刷进板子跑起来。
  4. 之后电脑脚本就能随时通过这个入口，让运行中的固件自己重启进 ROM 下载模式。

这段只有几行的代码里藏着三个非常关键的底层细节：

  1. AT(.volatile_ram_code) 把这个函数放进内部 RAM 里执行，因为执行过程中会关掉 RAM 保护并改变 Flash/SFC 状态，放在 RAM 里跑才能稳妥完成写标记和复位。
  2. nvram_set_boot_state() 并不是应用层自己写的函数，而是芯片出厂 Mask ROM 里固定地址的固件桩（Stub）。翻看链接脚本 cpu/br28/maskrom_stubs.ld 可以看到它被直接定义为绝对地址 nvram_set_boot_state = ABSOLUTE(0x1fdf0);，同一张符号表里还躺着 chip_reset = 0x1fdf4、usb_slave_mode = 0x1fe24、sfc_boot = 0x1fde4 等一系列 ROM 内置例程。这里传入的 UPGRADE_USB_SOFT_KEY 枚举值为 2（msd_upgrade.c 中定义了 NULL=0、USB_HARD_KEY=1、USB_SOFT_KEY=2、UART_KEY=3），ROM 会把这个状态值写进一块跨复位保留的存储区，供重启后的启动代码读取。
  3. JL_CLOCK->PWR_CON |= (1 << 4) 是直接往低速 SFR 区的时钟电源控制寄存器写软复位位（bit4，同族定义见 p11_app.h 的 LP_PWR_SOFT_RESET），故意绕过了 SDK 里常规走 p33_soft_reset() 的 cpu_reset() 函数（在 cpu.h 里那行操作 PWR_CON 的代码其实已经被注释掉了）。这里故意直接写寄存器，要的就是一次彻底干净的整芯片复位，让 CPU 直接从复位向量重新起跑并交由出厂 ROM 接管，而不是走普通的软复位路径。

2.4 复位后的下载入口

芯片完成整片软复位后，出厂 Mask ROM 的启动代码最先执行。当它读到保留区里的启动状态为 UPGRADE_USB_SOFT_KEY (2) 时，就会跳过从 Flash 加载应用固件的步骤，直接初始化 USB 从机进入 UBOOT1.00 下载模式，等待电脑端发指令。

需要注意，此时枚举出来的 ROM 下载设备使用的是独立的 boot_vid/boot_pid，跟刚才应用运行时枚举出来的 runtime_vid/runtime_pid 是两套完全不同的 USB 身份。电脑端的 usb_upgrade.py 调用 wait_sg(boot_vid, boot_pid) 等到下载设备上线后，会通过 /sys/bus/usb/devices 与 /sys/class/scsi_generic 核对切换前后的 USB 物理端口路径（比如 1-2.3），确认是同一块板子后，再调用 flash.py 执行后续刷写。

顺着这套 boot state 机制往外看，SDK 里一共提供了四类升级触发入口，而最终走 USB 还是串口下载，则由打包配置 isd_config_rule.c 与 isd_config.ini 中的 DOWNLOAD_MODEL = USB（可选 USB 或 SERIAL）决定：

升级入口 触发方式 对应的启动状态值与源码位置
USB 软 KEY 运行态固件收到 0xFC/0xFE 控制请求或私有 SCSI 0xFB/0xFD/0xFC 命令 写入 UPGRADE_USB_SOFT_KEY (2)，位于 msd_upgrade.c
USB 硬 KEY 外置下载器在芯片上电复位阶段发送 USB_KEY 物理握手波形，不依赖应用固件 识别为 UPGRADE_USB_HARD_KEY (1)，由出厂 ROM 直接处理
UART 串口/充电仓 通过耳机充电仓或串口发送升级指令触发 写入 UPGRADE_UART_KEY (3)，位于 cpu/br28/chargestore.c
官方配置工具 电脑侧配置工具下发在线命令触发 在 apps/common/config/new_cfg_tool.c 的 cfg_tool_go_mask_usb_updata() 中直接写死状态值 2

3、下载器烧录

一旦刷入的新固件存在 Bug 导致开机崩溃或死锁，无法响应上面的软件请求，就得靠外部工具在芯片上电复位的瞬间向 USB 引脚发送一段特殊的握手信号。芯片重跑出厂 ROM 代码时识别到这段握手波形，就会直接停留在 UBOOT1.00 下载模式，官方《升级与下载说明》中就有针对 AC701N 下载设备的演示。

要完成这次抢救，硬件上必须配合做好两件事：先让芯片真正复位重启以重新打开开机检测窗口，再赶在窗口期内把 USB_KEY 握手波形发进去。

3.1 USB_KEY 握手信号

根据开源社区的逆向记录，USB_KEY 握手信号的电气特征如下：

信号参数 逆向记录典型值
固定识别码 0x16EF（二进制 0001 0110 1110 1111）
发送位序 高位先发（MSB First）
物理传输形式 利用 USB D+ 和 D- 两根线，一根提供时钟，另一根传输数据
典型时钟频率 约 50 kHz，发完 16 位数据耗时约 320 μs
采样边沿与芯片响应 时钟上升沿采样数据；芯片识别成功后会将两根线同时拉低约 1～2 ms

关于时钟线与数据线的具体分配，同一大佬的 USB_KEY 专题页将 D+ 标为时钟、D- 标为数据，而在另一篇如何进入 UBOOT 的文档表述恰好相反。动手自制恢复工具时，建议在目标芯片上实测确认两根线的分工、开机握手窗口时间以及拉低响应波形。

这里有一个很多新手容易踩的坑，USB_KEY 是一段双线独立翻转的原始 GPIO 电平时序，不能用普通电脑的 USB 接口直接发送。电脑侧的 libusb 传输接口只能发起标准的控制、批量或中断传输，如果你把 0x16EF 当作普通 USB 数据包发出去，主机控制器硬件会自动给它套上 SYNC 同步头、PID 包标识、CRC 校验并做 NRZI 差分编码，到达引脚上的波形早就面目全非了。因此生成 USB_KEY 必须靠外部单片机的 GPIO 直接操作两根信号线。

3.2 芯片复位

最稳妥的复位办法是用外部下载器直接切断杰理芯片的电源，等板卡彻底放完电后再重新供电并发起握手。

官方强制升级工具的操作说明文档提到，在默认拨码下按下升级键会切断电源输出至少 250 ms 后再发起握手；自制恢复电路的具体断电等待时间则要看目标板电容的实际放电速度。

除了断电，另一种办法是触发芯片的长按复位引脚。例如 AC701N 工程在 board_701n_demo_cfg.h 和 cpu/br28/setup.c 的 setup_arch() 中默认将 PB1 配置为长按 8 秒低电平触发硬件复位。这种方式适合固件已经跑完早期硬件初始化、后来在业务循环里卡死的场景；如果刷入的坏固件在执行到 setup_arch() 配置复位引脚之前就崩溃了，拉低 PB1 同样无效，还是得靠断电或纯硬件复位路径。

4、RAM 加载程序接管 Flash

芯片进入 UBOOT1.00 模式后会枚举为一个 USB 大容量存储（MSC）设备。此时先使用 ROM 提供的基础内存读写和函数跳转能力；本文的 Flash 维护由随后上传的 RAM Loader 提供，电脑先把目标芯片对应的 Loader（比如我验证的 AC701N 使用的是 br28loader.uboot）上传到芯片 RAM 里跑起来。

在我的 Linux 主机上，jieli_uboot.py 通过打开对应的 /dev/sg* 字符设备，利用 SG_IO 接口发送 16 字节的杰理私有 SCSI 命令（有效参数不足 16 字节时在末尾补 0xFF）。这只是借用了标准 SCSI 的通道外壳，整个交互按以下命令顺序依次执行：

阶段操作 命令码 执行效果
确认设备身份 INQUIRY (0x12) 读取 36 字节标准设备信息，核对返回的产品标识是否为 UBOOT1.00
写入芯片 RAM 0xFB06 从目标 RAM 地址（如 AC701N 为 0x120000）起，按每块 512 字节上传 Loader 数据并校验 CCITT CRC16
调用 RAM 程序 0xFB08 跳转到 RAM 入口地址执行 Loader，并传入目标存储介质等两字节初始化参数
查询在线存储 0xFC0A、0xFC0B 由 Loader 返回存储介质类型（如 0x03 代表 SPI0 NOR）、容量指数与 3 字节 Flash JEDEC ID
读取 Flash 0xFD05 按指定起始地址和长度回读 Flash 数据
擦除与写入 Flash 0xFB00、0xFB01、0xFB04 分别执行 64KB 块擦除、4KB 扇区擦除，以及带 CRC16 校验的分块写入
启动应用固件 0xFC0C 结束下载会话，触发芯片复位并从 Flash 引导新固件

根据上游《USB loader protocol v2》对内存跳转的分析，芯片收到 0xFB08 调用 Loader 入口函数时，ROM 会把底层的 USB 收发与命令回调指针作为参数传给它，Loader 随即注册自己的命令处理表，从而无缝接管后续的 0xFC0A、0xFB04 等全部 Flash 读写命令。

5、Loader 来源与 SDK 容器解析

5.1 预编译 Loader 与 加扰

不同型号的杰理芯片需要使用各自匹配的 RAM Loader，开源项目 kagaimiq/jl-uboot-tool 的 data/loaderblobs/usb/ 目录下收集了多款主流杰理芯片的预编译二进制文件。以我验证的 AC701N 为例，原先保存为 br28loader.uboot、现在也随上游芯片资料提供的 br28loader.bin 是同一份数据，文件大小为 23,552 字节（SHA-256 为 ab1b77eb73385aaa78ab769253b2af7ef63d0ade46f391bd7424cc598a40267c）。

这里说的加扰和解扰，只是 ROM 与上位机之间对上传数据做的一层固定规则变换，跟后面的芯片加密密钥不是一回事。当前脚本直接调用上游仓库的对应算法，它的核心逻辑可以用下面几行 Python 看明白：

可以看到，杰理拿中文字符串 "孟黎我爱你，玉林"（GB2312 编码）当作种子，每处理一个字节就滚一次 CRC16，取算出来的低 8 位与原始数据做异或（^）。因为同一个字节对同一个数连续异或两次就会变回原样，所以加扰和解扰跑的是完全同一套函数。

芯片的出厂 ROM 在收到每个 0xFB06 数据块时，都会独立重置状态并跑一遍这个函数，把乱码还原成明文机器码再写入 RAM。由于上游仓库提供的这份 br28loader.uboot 在发布前已经提前做过了一次异或打乱（见上游配置定义与上传逻辑），因此主机配置文件中设置 loader_transform="none" 代表直接原样发送这份乱码文件，芯片收到后异或一次正好还原成可执行的明文程序。如果电脑上传前多此一举再调一次该函数，反而会把它还原成明文发过去，经芯片 ROM 再异或一次又变成乱码，程序直接跑飞。

5.2 原厂 SDK 的 JLFV 容器结构

在杰理各系列的官方 SDK 中也自带了对应的 Loader 文件，比如 AC701N SDK 的 cpu/br28/tools/download.sh 构建脚本会将 br28_loader_ftlv1.bin 复制为 br28loader.bin 供官方烧录工具调用。这类原厂文件外层带有 JLFV 容器，现有 Python 上传入口接收的是程序载荷，不能将整个容器文件直接当作 RAM 程序上传。

以我让ai拆解的 br28_loader_ftlv1.bin 和 br28_loader_ftlv2.bin 为例，其内部容器布局如下：

容器区域 字节偏移范围 存放内容与用途
容器总头 0x00～0x1f 固定 32 字节，经 ENC 解扰后可见 JLFV 魔数、文件总长度、目录记录数及头部 CRC16
两条目录记录 0x20～0x5f 每条 32 字节，分别描述后续各段的起始偏移、长度和段 CRC16
version 段 0x60～0xbf 记录 Loader 与底层驱动的版本字符串，仅用于主机核对，不上传到芯片
data 段 从 0xc0 到末尾 真正需要上传到芯片 RAM 的 MengLi 加扰程序数据

两份原厂 SDK 文件的具体尺寸对比如下：

SDK 文件名 容器文件总长度 提取出的 data 段长度
br28_loader_ftlv1.bin 33,984 字节 33,792 字节（0x8400）
br28_loader_ftlv2.bin 27,328 字节 27,136 字节（0x6a00）

这套容器的加扰与校验规则相当讲究，总头和每条目录记录都各自从初始状态独立做了一次 ENC 解扰，不能把整个文件头当成一段连续数据去解；而 data 段内部则保持其原有的传输加扰状态。校验方面全部采用初值为 0 的 CCITT CRC16 算法，其中总头 CRC 覆盖解扰后头部的 [6, 32) 字节，目录表 CRC 直接覆盖未解扰的原始目录表区域，各个内容段则各自拥有独立的 CRC16。

反汇编官方的 Linux 烧录工具也能印证这一流程，官方工具会先解析 JLFV 容器并校验各段 CRC，随后只提取出里面的 data 段上传到芯片 RAM 运行。由于当前的 Python 上传脚本直接接收裸二进制载荷，如果后续想尝试替换成 SDK 自带的 Loader，需要先按目录表校验并剥离出 data 段，再上板实测它的加载地址、加扰方式、启动参数和命令响应是否完全兼容。

6、下载模式下的探测、烧录与回读

6.1 烧录、回读与启动确认

芯片跑起匹配的 RAM Loader 后，脚本提供了探测、烧录和回读校验三个入口（块大小等参数在项目的 JSON 配置文件里指定，本文工程配的是 256 字节）：

脚本入口与参数 电脑与杰理执行的操作 结束后的设备状态
flash.py --probe 上传 RAM Loader，读取在线存储类型、Flash ID 并核对容量，不擦写 Flash 结束后不主动启动应用
verify_flash.py 分块读取镜像覆盖范围，逐字节比对并核对 SHA-256，不擦写 校验通过后请求启动应用
flash.py 擦除镜像覆盖范围并分块写入，按项目策略处理旧 OTA 区；默认不自动回读 写入后请求启动应用

调用时都要带上 --config 指定项目的 JSON 配置。如果给 verify_flash.py 加上 --via-usb，脚本会先通过前面说的运行态软入口把板子切进下载模式再回读；不带这个参数时，板子本身得已经处于下载模式。

另外芯片收到启动命令（0xFC0C）后会立刻复位断开 USB，经常来不及把 SCSI 应答包发回电脑。所以脚本做了兼容判断，只要收到有效应答，或者检测到同一个 USB 物理端口上重新枚举出了应用固件的运行态 USB 设备，就判定启动成功；随后再去读串口日志核对固件版本号和编译时间，确认跑起来的是最新刷入的代码。

6.3 RAM 保护范围与扩展命令差异

用命令行做 Flash write 或 erase 时，地址和长度必须满足 4 KB 扇区对齐且不能越界。做 RAM 调试写入时，脚本也会自动拦截覆盖当前 Loader 代码段的操作。

对于本文使用的 AC701N Loader，它还会额外占用并保护 0x120000 ~ 0x12ffff 这整段 64 KB 内存，往这个范围发写命令会直接导致当前下载会话断开。自己在 RAM 里做读写实验时，一定要避开 Loader 的代码区、工作区、栈以及 ROM 占用的内存，不能光看某个地址能读出数据就往上硬写。

另外上游通用协议库里有三个扩展查询命令，在这份 AC701N Loader 上表现特殊：

扩展查询 在 AC701N Loader 上的实际表现
status（0xFC03） 返回命令字段无效
loader-version（0xFC15） 不返回上游库预期的版本字符串，会触发短传输报错
rom-id（0xFC16） 上游库按读取命令发起，但这版 Loader 把它当成不同方向的数据接收命令，会导致会话卡死

这三项属于上游通用库与这版具体 Loader 二进制文件之间的指令集差异，日常在 AC701N 上做设备探测、Flash 擦写回读和启动完全用不到这三个扩展查询。

6.4 官方离线打包与芯片密钥

前面说的第三方大佬的加扰只是固定规则的传输变换，而杰理的 .key 芯片密钥才是用来给固件打包加密的。

脚本里的 package.py 调用了官方的 isd_download 工具，利用 bwrap 隔离出一个临时目录，加 -package-only 参数完成离线打包，生成最终的 jl_isd.bin 和 jl_isd.fw，不会污染 SDK 源码目录。需要加密钥打包时，直接通过 --key-file 传入即可：

不传 --key-file 就按默认的无密钥方式打包。在下载模式下可以用 key-info 查看芯片是否为空白状态，或者用 key-match --key-file <密钥文件> 比对密钥是否匹配。传统 .key 文件本身是 72 个十六进制字符，里面把 AES 解码材料和密文放在了一起，经 CRC 校验后提取出 16 位芯片密钥，所以密钥文件本身得靠文件权限保管好。

特别注意，离线加 key 打包、在线比对密钥，跟往芯片里烧写熔丝（key-burn）完全是两码事。一旦把密钥真正烧进芯片一次性熔丝（OTP），就再也没法靠重刷固件改回空白状态了，所以脚本默认把 key-burn 锁死关闭，防止误操作把板子锁死。

6.6 双 Bank 升级与擦写边界

目前 flash.py 刷入的是 Flash 基址镜像。如果工程开启了双 Bank OTA 且 Flash 里还留着上一次 OTA 升级写入的备用区代码，芯片重启后引导程序可能会继续跳进旧的升级 Bank，导致新刷的基址固件没生效。加上 --activate-base-bank 参数后，脚本会根据打包日志里的 CODE_BOUNDARY_LINE 和 VM_START_ADDR 自动擦除旧的 OTA 代码区，确保重启后一定跑新刷进去的基址固件。

最后还要注意，配置 Flash 擦除和烧录范围时一定要严格对照自己工程的分区布局，避开其他信息的存放区，别刷一次固件把板子的配对和校准数据全抹掉了。

7、自制电脑可控的恢复下载器

如果不想每次遇到坏固件都去手动插拔电源或按官方烧录盒按键，可以自己用一块带 USB 的小单片机做一个受电脑脚本控制的恢复下载器。这个小工具只需要把三件事接到电脑命令接口上，分别是切断与恢复目标板供电、用 GPIO 发送 USB_KEY 握手波形，以及通过模拟开关切换 USB 数据线走向。

flowchart LR
    A[电脑脚本] -->|发送操作命令| B[独立供电的恢复控制器]
    B -->|控制目标供电| C[负载开关或MOS电源电路]
    C --> D[杰理目标板]
    B -->|生成启动握手| E[USB数据线切换电路]
    A -->|握手成功后传输固件| E
    E -->|按阶段连接电脑或控制器| D

整套全自动恢复流程非常清晰，电脑脚本向恢复控制器发送救砖指令后，控制器先关断 MOS 管切断杰理目标板供电，延时等待电容放电完毕后重新合上供电，同时将模拟开关切到控制器一侧，用 GPIO 在 D+/D- 上打出 0x16EF 握手信号；检测到杰理拉低总线响应后，控制器立刻将自身 GPIO 设为高阻输入状态，并把模拟开关拨回电脑主机一侧，通知电脑脚本直接接管刚刚枚举出来的 UBOOT1.00 设备完成后续刷机。

目前开源社区里有两份现成的项目可以参考其电路和握手法：

开源参考项目 现成可复用的部分 改造成全自动工具还需补齐的部分
ESP32-S3 BR25 USB_KEY 工具 包含完整的接线图与 Arduino 固件，已实现 POWER_CTL 供电控制和 0x16EF 握手发送 原代码为上电自动单次执行，需补充电脑串口命令接收逻辑、USB 模拟开关切换控制及目标芯片时序核对
RP2040 Pico 下载器设计 给出了完整的 USB 信号切换电路、握手检测状态机及配套 C 源码 原设计将目标板 VBUS 直通、靠手动按键触发重启，需补上目标板供电开关电路与电脑命令接口

这两个方案刚好互补，前者写好了断电与握手动作，后者画好了把 D+/D- 交还给电脑的模拟开关切换电路。

不过必须吐槽一句，这两个国外项目之所以拿 ESP32-S3 或 RP2040 来做，纯粹是因为作者随手拿抽屉里现成的开发板飞线验证；如果真要自己画板做这个下载器，拿二三十块钱的双核 Wi-Fi 芯片只干“断电 + 打 16 个脉冲 + 切模拟开关”这三件事，纯属杀鸡用牛刀、白花冤枉钱。算下来整个控制器只需要 4 个普通 GPIO 和微秒级延时，随便选一颗一两块钱的廉价单片机（比如自带 USB 从机的 CH552G，或者几毛钱的 CH32V003、STC8G1K08）配一颗几毛钱的 CH442E 模拟开关，三五块钱就能搞定整块小板；只有当你打算连电脑和模拟开关都省掉、让单片机发完握手后自己切换成 USB Host 独立读写 Flash 时，才真正用得上 ESP32-S3 这类带 USB OTG 主机外设的芯片。

杰理官方的第四代强制升级工具其实也预留了类似的入口，官方《工具拨码开关说明》里提到将第 7 位拨码拨上去即可开启电脑通信模式，收到电脑发来的升级指令后会自动执行相当于按下升级键的动作。不过官方并没有公开这套上位机触发指令的具体字节格式，想要彻底实现自动化编译刷机还是自己用几块钱的单片机搭一块可控下载器最省心。
