杰理芯片 USB 烧录流程拆解

从系统启动流程、开机硬件握手、运行态软触发到 RAM Loader 擦写与自制下载器

暂时还没写完，仅供参考

折腾这套 USB 烧录并封装成 jieli-build 技能，初衷是让 AI 能够独立跑通“写代码 → 编译 → 烧录 → 验证”的闭环开发。只要在固件里留好 USB 升级响应接口，插一根 USB 数据线，AI 改完代码就能自己发命令把新固件刷进板子验证，不用每次人工去按下载器；万一 AI 写出坏固件把板子刷成砖，再配合一块几块钱的自制硬件下载器在芯片上电瞬间发握手脉冲救活，就能实现彻底的全自动闭环。

最初知道可以免烧录盒直刷，是在 Yandex 搜索方案时看到俄罗斯 USMI 论坛有大佬用 Arduino 玩杰理芯片，提到可以直接通过 USB 触发烧录，顺着这条线索把资料翻了一遍，才彻底摸顺了杰理的启动与下载流程。

本文代码与数据均以我实际验证过的 AC701N 工程为例，其他型号按对应 SDK 和编译配置确认即可。

1、启动与烧录流程

要搞懂杰理怎么刷机，得先看懂它平时正常上电是怎么一步步启动的。

1.1 杰理启动流程

杰理芯片平时正常开机，会按以下顺序跑三段程序：

  1. 第 1 步先跑死锁在芯片内部掩膜区的出厂 Mask ROM，它一上电最先醒来，先看芯片保留内存里有没有软升级标记，再看 USB 引脚上有没有外部发来的 0x16EF 硬件握手脉冲，两项都没有才去 Flash 里找下一棒。
  2. 第 2 步由 Mask ROM 跳进 Flash 开头的二级引导程序 Bootloader（如 uboot.boot），负责初始化 Flash 参数、核对双 Bank 分区并准备加载主程序。
  3. 第 3 步正式跳入 Flash 主程序区的应用固件 App，开始运行用户自己写的业务代码。

1.2 烧录触发原理

明白了正常启动的三步，那么刷机的核心思路就一句话，想办法把芯片拦在第 1 步的 Mask ROM 里，不让它往下读 Flash，让它直接变成电脑上的 UBOOT1.00 下载设备。

对应上面不同的启动阶段，拦截芯片进入下载模式只有两条路：

  • 硬件波形拦截发生在第 1 步刚上电的瞬间。外置下载器先给芯片断电再重新上电，趁 Mask ROM 刚醒来、还没去读 Flash 的头几毫秒，直接往 USB 引脚打 0x16EF 脉冲把芯片拦下来。因为此时根本还没走到 Flash 那一步，所以哪怕 Flash 里的代码全毁了（变砖了）也能救活。
  • 软件 USB 指令触发发生在第 3 步应用固件正常运行阶段。当板子已经开机跑起 App 并连上电脑 USB 时，电脑发一条私有 USB 指令给 App，App 收到后往芯片保留区写一个软升级标记，再主动触发整芯片复位退回第 1 步。Mask ROM 重新跑起来一看有标记，就主动停在下载模式。

    A["第1步：上电运行出厂Mask ROM"] -->|流程一：上电瞬间发0x16EF硬件波形| G["进入UBOOT1.00下载模式"]
    A -->|流程二：不发波形，正常引导| C["第2步：运行Flash 里的Bootloader"]

    G --> H["电脑上传临时程序到内存并运行"]

这里有个地方，有些芯片出厂自带的 Mask ROM 极其精简，它只懂“往内存（RAM）里写数据”和“跳过去执行”，自己根本没有擦写 Flash 的驱动。所以进入 UBOOT1.00 下载模式后，电脑还得先传一段临时加载程序（RAM Loader）到芯片 RAM 里跑起来，由这个临时小工接管 USB 去完成真正的 Flash 擦写，大佬 kagaimiq 对 UBOOT1.00 下载阶段的文档详细拆解了这套分工。

整个过程涉及的四段程序职责对比如下：

程序名称 存放位置 归属阶段与负责的工作 断电后的状态
出厂 Mask ROM 芯片内部固化的掩膜区 启动第 1 步最先执行，负责开机引导，或拦截进入 UBOOT1.00 提供基础 RAM 读写入口 永久保留，擦不掉
Flash Bootloader 随固件烧录进 Flash 开头（uboot.boot） 启动第 2 步执行，正常开机时引导应用固件，衔接 SDK 的启动与升级流程 保存在 Flash 中，随烧录更新
应用固件 App 烧录在 Flash 主程序区 启动第 3 步执行，跑用户业务代码；若开启软升级接口，可接收电脑指令写标记并复位 保存在 Flash 中，随烧录更新
RAM Loader 存放在电脑端，刷机时临时传进芯片 RAM 仅在刷机阶段运行，初始化存储驱动，向电脑提供 Flash 查询、读取、擦除与写入命令 断电即失，每次刷机重新上传

2、硬件强制下载

先看发生在启动第 1 步（Mask ROM 刚上电瞬间）的硬件强制下载方式。只要板子是个空片、或者刷入了坏固件开机即崩溃，就必须走这条路，官方《升级与下载说明》有完整演示。

2.1 握手流程

硬件触发发送的 USB_KEY 是一段双线独立翻转的原始 GPIO 时序，普通电脑的 libusb 传输接口只能发带协议头的标准差分包，发不出这种波形，必须靠外部单片机直接操作引脚（底层逆向细节可参考 USB_KEY 专题页与进入 UBOOT 文档）。

用大白话讲，强制下载器在第 1 步上电瞬间干的活就下面 8 步：

  1. 断开芯片电源，同时切断芯片与电脑之间的 DM、DP 信号线。
  2. 下载器把自己的 GPIO 连到芯片的 DM、DP 线上，并给芯片重新上电。
  3. 上电后立刻在 DP 线上发 50 kHz 的时钟脉冲，同时在 DM 线上发数据 0x16EF（二进制 0001 0110 1110 1111），高位先发（MSB 在前），上升沿有效。
  4. 发完一组 USB_KEY 后，立刻把 DM、DP 电平拉高。
  5. 检测 DM、DP 电平，如果还是高电平，就跳回第 3 步继续发。
  6. 只要检测到 DM 或 DP 任意一根线变成低电平，就说明芯片的 Mask ROM 已经识别握手、中断了正常启动过程。
  7. 下载器立刻断开自己与芯片的连接，把芯片的 DM、DP 线切回电脑一侧。
  8. 电脑枚举出 UBOOT1.00 下载设备，硬件握手任务完成。

如果下载器要插在多设备共享的 STT-Hub 上使用，为了抗干扰，需要在第 6 步检测到低电平之后、切回电脑之前，多加三步同步确认：

  1. 等待 DP 线恢复高电平。
  2. 向 DP 线精确发送相隔 1 ms 的负脉冲。
  3. 再次等待 DP 线变回高电平（若未变高则退回上一步重发负脉冲），确认无误后再断开下载器并把 DM、DP 切回电脑。

2.2 芯片复位

由于 Mask ROM 只在刚上电复位的极短窗口期内监听 0x16EF 波形，一旦芯片已经跑进第 2 步或第 3 步，再发波形它也听不见。所以硬件下载器最稳妥的做法就是直接切断杰理芯片电源，等电容放完电再重新上电握手（官方强制升级工具操作说明提到默认按下升级键会断电至少 250 ms）。

另一种复位办法是拉低芯片的复位引脚。但要是坏固件在初始化复位引脚之前就崩了，复位同样没用，所以硬件下载器一律走断电重启最靠谱。

3、软件触发下载

再看发生在启动第 3 步（应用固件 App 正常运行阶段）的软件触发方式。平时改代码调试时，如果每次刷机都要靠硬件断电打脉冲未免太折腾；只要让正在运行的 App 固件听懂一条“切换到下载模式”的 USB 请求，电脑脚本就能随时让板子自己重启进 Mask ROM 下载模式。

需要注意，板子能枚举出普通 USB 串口、声卡或 U 盘，不代表这个升级接口已经打开。接入只需要四步：

  1. 检查目标固件处理 USB 控制请求的回调函数里，有没有处理 0xFC/0xFE 私有请求并调用下载切换函数。
  2. 确认这段代码真正参与了编译并被注册到 USB 分发链路里；如果没有，按 SDK 的回调机制补上。
  3. 第一次先用硬件下载器，把带有这个接口的固件刷进板子跑起来。
  4. 之后电脑脚本就能在 App 运行时直接发指令触发升级，免去外挂硬件下载器。

负责把芯片送回第 1 步 Mask ROM 下载模式的 go_mask_usb_updata() 位于 apps/common/device/usb/device/msd_upgrade.c 中：

这段代码做了三件关键事：

  1. AT(.volatile_ram_code) 把函数放进内部 RAM 执行，因为执行中会关掉 RAM 保护并改变 Flash/SFC 状态，在 RAM 里跑才能稳妥完成写标记和复位。
  2. nvram_set_boot_state() 是出厂 Mask ROM 里固定地址的固件桩（在 cpu/br28/maskrom_stubs.ld 中直接定义为绝对地址 0x1fdf0）。这里传入的 UPGRADE_USB_SOFT_KEY 枚举值为 2，ROM 例程会把这个状态写进一块跨复位保留的存储区。

3.4 升级入口汇总

芯片复位回到第 1 步后，出厂 Mask ROM 读到保留区里的启动状态为 UPGRADE_USB_SOFT_KEY (2)，就会跳过 Flash 引导，直接初始化 USB 从机进入 UBOOT1.00 下载模式。

此时枚举出来的下载设备使用独立的 boot_vid/boot_pid，跟刚才 App 运行时的 runtime_vid/runtime_pid 是两套不同的 USB 身份。电脑端脚本等到下载设备上线后，会核对切换前后的 USB 物理端口路径（如 1-2.3），确认是同一块板子后再执行刷写。

把前面的硬件握手和这里的软件触发放在一起看，SDK 一共支持四类升级入口（最终走 USB 还是串口下载由 isd_config.ini 中的 DOWNLOAD_MODEL = USB 决定）：

升级入口 所处启动阶段与触发方式 对应的启动状态值与处理位置
USB 硬 KEY 第 1 步刚上电瞬间，外置下载器发送 0x16EF 物理握手波形，不依赖 Flash 固件 识别为 UPGRADE_USB_HARD_KEY (1)，由出厂 Mask ROM 直接处理
USB 软 KEY 第 3 步 App 运行阶段，收到 0xFC/0xFE 控制请求或私有 SCSI 0xFB/0xFD/0xFC 命令 写入 UPGRADE_USB_SOFT_KEY (2) 并软复位，位于 msd_upgrade.c
UART 串口/充电仓 第 3 步 App 运行阶段，通过耳机充电仓或串口发送升级指令触发 写入 UPGRADE_UART_KEY (3) 并软复位，位于 cpu/br28/chargestore.c
官方配置工具 第 3 步 App 运行阶段，电脑配置工具下发在线命令触发 在 apps/common/config/new_cfg_tool.c 中直接写入状态值 2 并软复位

4、Flash 读写协议

无论走第 2 节的硬件波形还是第 3 节的软件指令，芯片现在都已经停在 Mask ROM 的 UBOOT1.00 模式，并在电脑上枚举为一个 USB 大容量存储（MSC）设备。接下来电脑就要先把对应芯片的 RAM Loader（如 AC701N 使用 br28loader.uboot）传进芯片内存跑起来，再由它擦写 Flash。

4.1 SCSI 命令交互

在 Linux 主机上，jieli_uboot.py 打开对应的 /dev/sg* 字符设备，通过 SG_IO 接口发送 16 字节的杰理私有 SCSI 命令（不足 16 字节时末尾补 0xFF），按以下顺序完成交互：

阶段操作 命令码 执行主体与效果
确认设备身份 INQUIRY (0x12) Mask ROM 响应 36 字节设备信息，核对产品标识是否为 UBOOT1.00
写入芯片 RAM 0xFB06 Mask ROM 接收数据，从目标 RAM 地址（AC701N 为 0x120000）起按 512 字节分块写入并校验 CRC16
调用 RAM 程序 0xFB08 Mask ROM 跳转到 RAM 入口地址执行 RAM Loader，并传入目标存储介质等两字节初始化参数
查询在线存储 0xFC0A、0xFC0B RAM Loader 返回存储介质类型（如 0x03 代表 SPI0 NOR）、容量指数与 3 字节 Flash JEDEC ID
读取 Flash 0xFD05 RAM Loader 按指定起始地址和长度回读 Flash 数据
擦除与写入 Flash 0xFB00、0xFB01、0xFB04 RAM Loader 分别执行 64KB 块擦除、4KB 扇区擦除，以及带 CRC16 校验的分块写入
启动应用固件 0xFC0C RAM Loader 结束下载会话，触发芯片复位并正常引导 Flash 中的新固件

根据上游《USB loader protocol v2》对内存跳转的分析，芯片收到 0xFB08 跳转到 Loader 入口函数时，Mask ROM 会把底层的 USB 收发与命令回调指针作为参数传给它，Loader 随即注册自己的命令处理表，无缝接管后续所有的 Flash 读写指令。

4.2 Loader 加扰

开源项目 kagaimiq/jl-uboot-tool 的 data/loaderblobs/usb/ 目录下收集了多款主流杰理芯片的预编译 Loader（AC701N 对应的 br28loader.uboot / br28loader.bin 大小为 23,552 字节）。

电脑往 Mask ROM 上传 Loader 数据块时，双方约定了一层名为 MengLi 的固定规则异或加扰（这只是传输层变换，跟后面的芯片加密密钥不是一回事）：

杰理拿中文字符串 "孟黎我爱你，玉林"（GB2312 编码）当作种子，每处理一个字节滚一次 CRC16，取低 8 位与数据做异或（^）。芯片 Mask ROM 每收到一个 0xFB06 数据块，都会跑一遍这个函数把乱码还原成明文机器码再写入 RAM。由于上游仓库提供的 br28loader.uboot 发布前已经提前做过了一次异或打乱（见上游配置定义与上传逻辑），所以配置 loader_transform="none" 直接原样发送这份文件，芯片收到后异或一次正好还原成明文程序。

4.3 JLFV 容器

杰理官方 SDK 里也自带了 Loader 文件（如 cpu/br28/tools/ 下的 br28_loader_ftlv1.bin 和 br28_loader_ftlv2.bin），但原厂文件外层包了一层 JLFV 容器，不能整包直接塞进 RAM，必须先剥离出里面的 data 段载荷：

容器区域 字节偏移范围 存放内容与用途
容器总头 0x00～0x1f 固定 32 字节，经 ENC 解扰后可见 JLFV 魔数、文件总长度、目录记录数及头部 CRC16
两条目录记录 0x20～0x5f 每条 32 字节，分别独立做 ENC 解扰，描述后续各段的起始偏移、长度和段 CRC16
version 段 0x60～0xbf 记录 Loader 与底层驱动的版本字符串，仅用于主机核对，不上传到芯片
data 段 从 0xc0 到末尾 真正需要上传到芯片 RAM 的 MengLi 加扰程序载荷（如 ftlv1 总长 33,984 字节，剥离后 data 段为 33,792 字节）

5.2 芯片密钥

前面说的 MengLi 加扰只是固定规则的传输变换，而杰理的 .key 芯片密钥才是真正用来给固件加密验签的。玩杰理板子前，先记住三条关于 key 的铁律（详见杰理开发大佬在电子发烧友与搜狐文章里的说明，以及立创社区的硬件改造心得和编译烧录记录）：

  1. 早年的 AC690x 系列芯片没有 key 限制，刷机不需要 key 文件。
  2. 单独买的全新空白 IC 内部未烧熔丝，不需要 key 文件（买之前需向卖家问清楚）。
  3. 凡是购买现成的成品板做二次开发，一定需要厂家匹配的 key 文件，不要抱侥幸心理。因为商品板出货前必然要校准（trim）晶振匹配电容和 LDO 电压值，产线顺手就把芯片的 efuse 密钥一起烧了。

关于杰理开发环境搭建与 SDK 获取，可直接查阅杰理官方开发工具文档、杰理 Gitee 开源仓库以及云思客文档中心。

下载模式下可以用 key-info 查看芯片是否为空白状态，或用 key-match --key-file <密钥文件> 比对密钥是否匹配。另外，离线加 key 打包与往芯片一次性熔丝（OTP）里烧写密钥（key-burn）是两码事，一旦烧进熔丝就永远改不回空白状态，所以脚本默认把 key-burn 锁死关闭。

5.3 分区边界

目前 flash.py 刷入的是 Flash 基址镜像。如果工程开启了双 Bank OTA 且 Flash 里还留着上一次 OTA 升级写入的备用区代码，芯片重启后第 2 步的引导程序可能会继续跳进旧的升级 Bank，导致新刷的基址固件没生效。加上 --activate-base-bank 参数后，脚本会根据打包日志里的 CODE_BOUNDARY_LINE 和 VM_START_ADDR 自动擦除旧的 OTA 代码区，确保重启后一定跑新刷进去的基址固件。同时配置擦写范围时要核对分区布局，避开板子的蓝牙配对和校准数据区。

6、自制下载器

回头看第 2 节的硬件波形触发流程，自己做一块强制下载器其实非常简单，核心就三件事：控制目标板供电通断、在第 1 步上电瞬间用单片机 GPIO 发 0x16EF 握手波形、检测到芯片拉低响应后用模拟开关把 USB 数据线切回给电脑。

flowchart LR
    A[电脑主机] -->|下载通信| E[USB模拟开关]
    B[控制单片机] -->|控制供电通断| C[电源开关电路]
    C --> D[杰理目标板]
    B -->|上电瞬间发0x16EF并切换通道| E
    E -->|分时连接单片机或电脑| D

立创开源平台上已经有非常成熟、仅需几块钱的低成本方案，另有国外的开发板飞线方案可供对比参考：

开源项目 硬件方案与特点
自制杰理下载器 V3 / 自制二合一下载器 V3 极简高性价比方案，直接采用廉价的 STC15W101 单片机配合 FSUSB30 USB 模拟开关芯片实现自动断电、握手与通道切换；同作者还开源了配套的拼多多 35 元拼音学习机抄板电路以及逻辑分析仪屏幕初始化抓包和触控抓包分析
