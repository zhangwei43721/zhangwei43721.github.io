杰理芯片 USB 烧录流程拆解

从运行态软触发、开机硬件握手到 RAM Loader 与 Flash 读写全流程

折腾这套纯软件 USB 烧录并把它封装成 jieli-build 技能（Skill），初衷是为了让 AI 能够独立跑通“写代码 → 编译 → 烧录 → 验证”的闭环开发。只要在固件里加上 USB 升级响应接口，AI 改完代码就能自己发命令把新固件刷进板子验证，不需要每次都由人工去按官方烧录盒；等后面有空再做一块几块钱的电脑可控硬件下载器，就算 AI 写出了坏固件把板子刷成砖，也能自己调硬件断电握手把板子救活，实现彻底的全自动闭环。

最初知道可以免烧录盒直刷，是在 Yandex 搜索方案时看到俄罗斯 USMI 论坛上有大佬用 Arduino 玩杰理芯片，提到可以直接通过 USB 触发烧录，顺着这条线索把 SDK 翻了一遍，才彻底摸清了杰理底层的下载机制。

给支持 USB 下载的杰理芯片刷机分两种情况。板子上的应用固件正常运行时，只要我们在固件里开启并添加了 USB 升级响应代码，插一根普通 USB 数据线就能由电脑脚本直接触发刷机；如果刷入了损坏的固件导致死机或启动崩溃，应用里的接口跑不起来，就得在芯片上电复位阶段靠外部硬件发握手信号救砖。这两种方式只是进入下载模式的入口不同，进去之后走的是同一套 USB 下载通道。

这套软触发、开机硬件握手与 RAM Loader 接管机制在杰理多款芯片系列上是通用的，区别主要在于不同芯片型号对应的 Loader 文件、加载地址和加扰配置不同。本文的具体代码、寄存器与容器拆解数据均以我实际验证过的杰理 AC701N 工程为例，换用其他型号时按对应 SDK 核对替换即可。

1、整体烧录流程

电脑通过 USB 烧录杰理芯片的全过程分为三个阶段，先让芯片进入 ROM 下载模式，接着把临时加载程序传进芯片 RAM 运行，最后由这段 RAM 程序完成 Flash 擦写。

flowchart TD
    A[电脑发起烧录] --> B{杰理应用能否响应USB请求}
    B -->|能够响应| C[应用接收请求并切换到ROM下载模式]
    B -->|已经无法响应| D[外置工具使杰理复位并发送启动握手]
    D --> E[杰理ROM识别握手并进入下载模式]
    C --> F[电脑识别杰理下载设备]
    E --> F
    F --> G[电脑上传临时程序到杰理RAM并调用]
    G --> H[临时程序执行查询和Flash读写]
    H --> I[电脑发送启动命令]
    I --> J[杰理启动Flash中的固件]

整个过程中涉及三段职责完全不同的程序：

程序名称 存放位置 负责的工作 断电后的状态
ROM 启动程序 芯片出厂固化的掩膜存储区 上电最先执行，负责正常引导或提供基础下载入口 永久保留
RAM 临时加载程序（Loader） 存放在电脑端，刷机时上传到芯片 RAM 初始化存储驱动，向电脑提供 Flash 查询、读取、擦除与写入命令 断电即失，每次刷机重新上传
Flash 启动程序（Bootloader） 随固件烧录进 Flash（如 uboot.boot） 正常开机时引导应用固件，衔接 SDK 的启动与升级流程 保存在 Flash 中，随烧录更新

板子平时正常开机走的是“ROM 启动程序 → Flash 启动程序 → 应用固件”这条路；而电脑刷机走的是“ROM 下载入口 → RAM 临时加载程序 → Flash 读写操作”这条路，大佬kagaimiq的文档对 UBOOT1.00 下载阶段的说明详细解释了这套分工。

所以救砖的核心逻辑很简单，只要能让芯片重新跑一次出厂 ROM，并在开机瞬间拦住它进入下载模式，后续的 Flash 擦写全由电脑现场传进 RAM 的 Loader 接管，哪怕 Flash 里的原有程序全毁了也不影响重刷。

2、固件正常时的软触发切换

2.1 主机与设备侧的私有请求交互

芯片出厂固件默认并不一定会开启 USB 在线升级入口，为了配合 jieli-build 脚本实现免按键自动刷机，需要先在固件工程中启用 USB 从机并加上对应的请求响应逻辑。硬件上直接把电脑连到杰理芯片原生 USB 的 D+ 和 D- 引脚即可。

电脑端的 usb_upgrade.py 脚本通过 libusb 向控制端点 EP0 连发两次参数几乎完全相同的私有控制请求，唯一区别在于请求长度 wLength：

控制传输请求参数 作用与预期响应
bmRequestType=0x83、bRequest=0 (GET_STATUS)、wValue=0xFC、wIndex=0xFE、wLength=8 探测固件是否加入了在线升级入口，支持时会返回 8 字节 0xFF
保持相同的请求头参数，仅将 wLength 改为 0 正式触发切换，通知固件重启并跳入 ROM 下载模式

这段只有几行的代码里藏着三个非常关键的底层细节：

  1. 函数头部的 AT(.volatile_ram_code) 属性绝对不能省。因为调用 ram_protect_close() 等底层操作后，Flash 和 SFC 控制器的状态已经受到影响，不能保证 CPU 还能继续正常从 Flash 取指，所以整段函数必须放在掉电保留的内部 RAM 里跑才能安全执行到底。
  2. nvram_set_boot_state() 并不是应用层自己写的函数，而是芯片出厂 Mask ROM 里固定地址的固件桩（Stub）。翻看链接脚本 cpu/br28/maskrom_stubs.ld 可以看到它被直接定义为绝对地址 nvram_set_boot_state = ABSOLUTE(0x1fdf0);，同一张符号表里还躺着 chip_reset = 0x1fdf4、usb_slave_mode = 0x1fe24、sfc_boot = 0x1fde4 等一系列 ROM 内置例程。这里传入的 UPGRADE_USB_SOFT_KEY 枚举值为 2（msd_upgrade.c 中定义了 NULL=0、USB_HARD_KEY=1、USB_SOFT_KEY=2、UART_KEY=3），ROM 会把这个状态值写进一块跨复位保留的存储区，供重启后的启动代码读取。
  3. JL_CLOCK->PWR_CON |= (1 << 4) 是直接往低速 SFR 区的时钟电源控制寄存器写软复位位（bit4，同族定义见 p11_app.h 的 LP_PWR_SOFT_RESET），故意绕过了 SDK 里常规走 p33_soft_reset() 的 cpu_reset() 函数（在 cpu.h 里那行操作 PWR_CON 的代码其实已经被注释掉了）。这里故意直接写寄存器，要的就是一次彻底干净的整芯片复位，让 CPU 直接从复位向量重新起跑并交由出厂 ROM 接管，而不是走普通的软复位路径。

2.3 复位后 ROM 的动作与四条升级入口

芯片完成整片软复位后，出厂 Mask ROM 的启动代码最先执行。当它读到保留区里的启动状态为 UPGRADE_USB_SOFT_KEY (2) 时，就会跳过从 Flash 加载应用固件的步骤，直接初始化 USB 从机进入 UBOOT1.00 下载模式，等待电脑端发指令。

需要注意，此时枚举出来的 ROM 下载设备使用的是独立的 boot_vid/boot_pid，跟刚才应用运行时枚举出来的 runtime_vid/runtime_pid 是两套完全不同的 USB 身份。电脑端的 usb_upgrade.py 调用 wait_sg(boot_vid, boot_pid) 等到下载设备上线后，会通过 /sys/bus/usb/devices 与 /sys/class/scsi_generic 核对切换前后的 USB 物理端口路径（比如 1-2.3），确认是同一块板子后，再调用 flash.py 把 RAM Loader 和固件镜像推上去。

顺着这套 boot state 机制往外看，杰理 SDK 其实围绕它设计了四条平行的升级触发入口，而最终走 USB 还是串口下载，则由打包配置 isd_config_rule.c 与 isd_config.ini 中的 DOWNLOAD_MODEL = USB（可选 USB 或 SERIAL）决定：

升级入口 触发方式 对应的启动状态值与源码位置
USB 软 KEY（日常主力） 运行态固件收到 0xFC/0xFE 控制请求或私有 SCSI 0xFB/0xFD/0xFC 命令 写入 UPGRADE_USB_SOFT_KEY (2)，位于 msd_upgrade.c
USB 硬 KEY（救砖主力） 外置下载器在芯片上电复位阶段发送 USB_KEY 物理握手波形，不依赖应用固件 识别为 UPGRADE_USB_HARD_KEY (1)，由出厂 ROM 直接处理
UART 串口/充电仓 通过耳机充电仓或串口发送升级指令触发 写入 UPGRADE_UART_KEY (3)，位于 cpu/br28/chargestore.c
官方配置工具 电脑侧配置工具下发在线命令触发 在 apps/common/config/new_cfg_tool.c 的 cfg_tool_go_mask_usb_updata() 中直接写死状态值 2

这套软切换的前提是应用固件还活着、能正常跑进 USB 中断。一旦 AI 写出的新固件有 Bug 导致开机就崩或者死锁，电脑发控制请求就彻底没戏了，这时候就得靠下一节的 USB 硬 KEY 握手入口来救砖。

3、固件损坏时的开机硬件握手

杰理官方的强制升级工具（烧录盒）能够在芯片上电复位的瞬间向 USB 引脚发送一段特殊的握手信号。芯片重跑出厂 ROM 代码时一旦识别到这段握手波形，就会放弃加载 Flash 里的坏固件，直接停留在 UBOOT1.00 下载模式，官方《升级与下载说明》中就有针对 AC701N 下载设备的演示。

要完成这次抢救，硬件上必须配合做好两件事：先让芯片真正复位重启以重新打开开机检测窗口，再赶在窗口期内把 USB_KEY 握手波形发进去。

3.1 USB_KEY 握手信号

根据开源社区的逆向记录，USB_KEY 握手信号的电气特征如下：

信号参数 逆向记录典型值
固定识别码 0x16EF（二进制 0001 0110 1110 1111）
发送位序 高位先发（MSB First）
物理传输形式 利用 D+ 和 D- 两根线，一根提供时钟，另一根传输数据
典型时钟频率 约 50 kHz，发完 16 位数据耗时约 320 μs
采样边沿与芯片响应 时钟上升沿采样数据；芯片识别成功后会将两根线同时拉低约 1～2 ms

关于时钟线与数据线的具体分配，同一大佬的 USB_KEY 专题页将 D+ 标为时钟、D- 标为数据，而在另一篇如何进入 UBOOT 的文档中文字表述恰好相反。动手自制恢复工具时，建议在目标芯片上实测确认两根线的分工、开机握手窗口时间以及拉低响应波形。

这里有一个很多新手容易踩的坑，USB_KEY 是一段双线独立翻转的原始 GPIO 电平时序，不能用普通电脑的 USB 接口直接发送。电脑侧的 libusb 传输接口只能发起标准的控制、批量或中断传输，如果你把 0x16EF 当作普通 USB 数据包发出去，主机控制器硬件会自动给它套上 SYNC 同步头、PID 包标识、CRC 校验并做 NRZI 差分编码，到达引脚上的波形早就面目全非了。因此生成 USB_KEY 必须靠外部单片机的 GPIO 直接操作两根信号线。

3.2 让芯片真正复位

最稳妥的复位办法是用外部控制器操纵负载开关或 MOS 管电路，直接切断杰理芯片的电源，等板载滤波电容彻底放完电后再重新供电并发起握手。在这期间，外部恢复控制器自身必须保持独立供电。

**对于接了锂电池的设备，必须同时核对电池和 USB 两条供电路径；如果电池一直在给杰理芯片供电，光靠断开 USB 5V 根本无法让芯片断电复位。**此外还要留意板子上其他带电芯片是否会通过 GPIO 信号线向杰理反向漏电。

官方强制升级工具的操作说明提到，在默认拨码下按下升级键会切断电源输出至少 250 ms 后再发起握手；自制恢复电路的具体断电等待时间则要看目标板电容的实际放电速度。

除了断电，另一种办法是触发芯片的长按复位引脚。例如 AC701N 工程在 board_701n_demo_cfg.h 和 cpu/br28/setup.c 的 setup_arch() 中默认将 PB1 配置为长按 8 秒低电平触发硬件复位。这种方式适合固件已经跑完早期硬件初始化、后来在业务循环里卡死的场景；如果刷入的坏固件在执行到 setup_arch() 配置复位引脚之前就崩溃了，拉低 PB1 同样无效，还是得靠断电或纯硬件复位路径。

4、RAM 加载程序接管 Flash

无论是通过软件请求切换，还是靠硬件 USB_KEY 握手拦停，芯片最终都会进入 UBOOT1.00 模式并枚举为一个 USB 大容量存储（MSC）设备。此时芯片里的出厂 ROM 只具备最基础的写内存和函数跳转能力，本身没有全套 Flash 擦写驱动，电脑必须先把目标芯片对应的 Loader（比如我验证的 AC701N 使用的是 br28loader.uboot）上传到芯片 RAM 里跑起来。

在我的 Linux 主机上，jieli_uboot.py 可以通过打开对应的 /dev/sg* 字符设备，利用 SG_IO 接口发送 16 字节的杰理私有 SCSI 命令（有效参数不足 16 字节时在末尾补 0xFF）。这里只是借用了标准 SCSI 的通道外壳，实际交互全按杰理自定义协议走：

  1. 电脑发送标准 INQUIRY 命令（12 00 00 00 24 00）读取 36 字节设备信息，核对返回的产品标识是否为 UBOOT1.00。
  2. 从目标芯片规定的 RAM 加载地址（例如 AC701N 为 0x120000）开始，按每块 512 字节循环发送 0xFB06 命令上传 Loader 二进制数据，每次请求都在命令块里附带写入地址、块长度和 CCITT CRC16 校验值。
  3. 上传完毕后发送 0xFB08 命令，让芯片跳转到该 RAM 地址执行 Loader，并传入目标存储介质等初始化参数。
  4. 根据上游《USB loader protocol v2》对内存跳转的分析，ROM 调用 Loader 入口函数时会把底层的 USB 收发与命令回调指针传给它，Loader 随即注册自己的命令处理表，无缝接管后续的 USB 通信。
  5. 电脑发送 0xFC0A 和 0xFC0B 查询在线存储设备类型与 Flash JEDEC ID，确认是预期容量的 SPI0 NOR Flash 后，执行分块擦除、写入或读取。
  6. 全部操作完成后，电脑发送 0xFC0C 命令通知芯片重启并引导新固件。

主机端用到的核心私有 SCSI 命令汇总如下：

阶段操作 命令码 执行效果
写入芯片 RAM 0xFB06 将单块 512 字节数据写入指定的芯片 RAM 地址并校验 CRC16
调用 RAM 程序 0xFB08 跳转到指定的 RAM 入口地址执行 Loader，并传入两字节参数
查询在线存储 0xFC0A、0xFC0B 返回存储介质类型（如 0x03 为 SPI0 NOR）、容量指数与 3 字节 Flash ID
读取 Flash 0xFD05 按指定起始地址和长度回读 Flash 数据
擦除与写入 Flash 0xFB00、0xFB01、0xFB04 分别执行 64KB 块擦除、4KB 扇区擦除，以及带 CRC16 的分块写入
启动应用固件 0xFC0C 结束下载会话，触发芯片复位并从 Flash 启动应用

5、Loader 来源与 SDK 容器解析

5.1 预编译 Loader 与 MengLi 加扰

不同型号的杰理芯片需要使用各自匹配的 RAM Loader，大佬的开源项目 kagaimiq/jl-uboot-tool 的 data/loaderblobs/usb/ 目录下收集了多款主流杰理芯片的预编译二进制文件。以我验证的 AC701N 为例，脚本实际上传的 br28loader.uboot 文件大小为 23,552 字节（SHA-256 为 ab1b77eb73385aaa78ab769253b2af7ef63d0ade46f391bd7424cc598a40267c）。

这里提到的“加扰”和“解扰”，其实就是用固定规则把原始数据打乱成乱码、再用同一规则还原回来的简易对称加密，用来防止别人直接反汇编看穿里面的明文机器码。从上一节的 mengli_transform() 代码可以看到，杰理拿中文字符串 "孟黎我爱你，玉林"（GB2312 编码）当作种子，每处理一个字节就滚一次 CRC16，取算出来的低 8 位与原始数据做异或（^）。因为同一个字节对同一个数连续异或两次就会变回原样，所以加扰和解扰跑的是完全同一套函数。

芯片的出厂 ROM 在收到每个 0xFB06 数据块时，都会自动跑一遍这个函数把乱码还原成明文机器码再写入 RAM。由于上游仓库提供的这份 br28loader.uboot 在发布前已经提前做过了一次异或打乱（见上游配置定义与上传逻辑），因此主机配置文件中设置 loader_transform="none" 代表直接原样发送这份乱码文件，芯片收到后异或一次正好还原成可执行的明文程序。如果电脑上传前多此一举再调一次该函数，反而会把它还原成明文发过去，经芯片 ROM 再异或一次又变成乱码，程序直接跑飞。

5.2 原厂 SDK 的 JLFV 容器结构

在杰理各系列的官方 SDK 中也自带了对应的 Loader 文件，比如 AC701N SDK 的 cpu/br28/tools/download.sh 构建脚本会将 br28_loader_ftlv1.bin 复制为 br28loader.bin 供官方烧录工具调用。但如果你直接拿 SDK 里的这个 .bin 文件喂给上面的 Python 脚本上传，芯片一定会跑飞，因为原厂 SDK 的 Loader 文件外层套了一层 JLFV 容器。

以我离线拆解的 br28_loader_ftlv1.bin 和 br28_loader_ftlv2.bin 为例，其内部容器布局如下：

容器区域 字节偏移范围 存放内容与用途
容器总头 0x00～0x1f 固定 32 字节，经 ENC 解扰后可见 JLFV 魔数、文件总长度、目录记录数及头部 CRC16
两条目录记录 0x20～0x5f 每条 32 字节，分别描述后续各段的起始偏移、长度和段 CRC16
version 段 0x60～0xbf 记录 Loader 与底层驱动的版本字符串，仅用于主机核对，不上传到芯片
data 段 从 0xc0 到末尾 真正需要上传到芯片 RAM 的 MengLi 加扰程序数据

两份原厂 SDK 文件的具体尺寸对比如下：

SDK 文件名 容器文件总长度 提取出的 data 段长度
br28_loader_ftlv1.bin 33,984 字节 33,792 字节（0x8400）
br28_loader_ftlv2.bin 27,328 字节 27,136 字节（0x6a00）

这套容器的加扰与校验规则相当讲究，总头和每条目录记录都各自从初始状态独立做了一次 ENC 解扰，不能把整个文件头当成一段连续数据去解；而 data 段内部则保持其原有的传输加扰状态。校验方面全部采用初值为 0 的 CCITT CRC16 算法，其中总头 CRC 覆盖解扰后头部的 [6, 32) 字节，目录表 CRC 直接覆盖未解扰的原始目录表区域，各个内容段则各自拥有独立的 CRC16。

反汇编官方的 Linux 烧录工具也能确认这一过程，官方工具会先解析 JLFV 容器并校验各段 CRC，随后只提取出里面的 data 段，按每块 512 字节通过 0xFB06 上传到 -boot 0x120000 指定的地址，最后带上 -div8 等时钟分频与存储选择参数调用 0xFB08 启动。由于目前的 Python 刷机脚本只负责裸传二进制载荷，若想换用原厂 SDK 里的 Loader，必须先按目录表解析校验并将 data 段单独剥离出来。

6、下载模式下的探测、烧录与回读

芯片跑起 RAM Loader 后，主机侧的 flash.py 和 verify_flash.py 提供了三种不同程度的操作入口：

脚本入口与参数 电脑与杰理芯片执行的操作 结束后的设备状态
flash.py --probe 上传并运行 RAM Loader，读取在线存储类型、Flash ID 并核对容量，全程不擦写 Flash 停留在当前下载模式，不发送启动应用命令
verify_flash.py 按每块 256 字节回读镜像覆盖范围的 Flash 数据，在电脑端逐字节比对并校验 SHA-256 比对通过后发送 0xFC0C 启动应用固件
flash.py 擦除目标区域并按每块 256 字节写入 jl_isd.bin，按需清理旧 OTA 代码区 写入完成后发送 0xFC0C 启动应用固件

回读比对是在电脑端内存中完成的，芯片上的 RAM Loader 只管响应 0xFD05 把指定地址的 Flash 原始字节读上来。

在执行 flash.py 正常烧录时，脚本会优先对满足 64KB 对齐的区间使用 0xFB00 块擦除，剩余尾部按 4KB 扇区使用 0xFB01 擦除，然后再分块写入 jl_isd.bin。对于开启了双备份 OTA 的工程，如果只更新基址固件而保留第二备份区的旧固件，芯片重启后仍可能跳去运行旧版本。为此脚本提供了 --activate-base-bank 选项，开启后会先读取打包日志核对 CODE_BOUNDARY_LINE 与 VM_START_ADDR 边界，确认无误后将旧 OTA 代码区一并擦空：

擦除和烧录的地址范围必须严格按当前工程的镜像布局设定，绝对不能越界擦除存放用户配置、蓝牙配对记录和出厂校准参数的 VM 区与工厂数据区。

7、自制电脑可控的恢复下载器

如果不想每次遇到坏固件都去手动插拔电源或按官方烧录盒按键，可以自己用一块带 USB 的小单片机做一个受电脑脚本控制的恢复下载器。这个小工具只需要把三件事接到电脑命令接口上，分别是切断与恢复目标板供电、用 GPIO 发送 USB_KEY 握手波形，以及通过模拟开关切换 USB 数据线走向。

flowchart LR
    A[电脑脚本] -->|发送操作命令| B[独立供电的恢复控制器]
    B -->|控制目标供电| C[负载开关或MOS电源电路]
    C --> D[杰理目标板]
    B -->|生成启动握手| E[USB数据线切换电路]
    A -->|握手成功后传输固件| E
    E -->|按阶段连接电脑或控制器| D

整套全自动恢复流程非常清晰，电脑脚本向恢复控制器发送救砖指令后，控制器先关断 MOS 管切断杰理目标板供电，延时等待电容放电完毕后重新合上供电，同时将模拟开关切到控制器一侧，用 GPIO 在 D+/D- 上打出 0x16EF 握手信号；检测到杰理拉低总线响应后，控制器立刻将自身 GPIO 设为高阻输入状态，并把模拟开关拨回电脑主机一侧，通知电脑脚本直接接管刚刚枚举出来的 UBOOT1.00 设备完成后续刷机。

目前开源社区里有两份现成的项目可以参考其电路和握手法：

开源参考项目 现成可复用的部分 改造成全自动工具还需补齐的部分
ESP32-S3 BR25 USB_KEY 工具 包含完整的接线图与 Arduino 固件，已实现 POWER_CTL 供电控制和 0x16EF 握手发送 原代码为上电自动单次执行，需补充电脑串口命令接收逻辑、USB 模拟开关切换控制及目标芯片时序核对
RP2040 Pico 下载器设计 给出了完整的 USB 信号切换电路、握手检测状态机及配套 C 源码 原设计将目标板 VBUS 直通、靠手动按键触发重启，需补上目标板供电开关电路与电脑命令接口

这两个方案刚好互补，前者写好了断电与握手动作，后者画好了把 D+/D- 交还给电脑的模拟开关切换电路。不过必须吐槽一句，这两个国外项目之所以拿 ESP32-S3 或 RP2040 来做，纯粹是因为作者随手拿抽屉里现成的开发板飞线验证；如果真要自己画板做这个下载器，拿二三十块钱的双核 Wi-Fi 芯片只干“断电 + 打 16 个脉冲 + 切模拟开关”这三件事，纯属杀鸡用牛刀、白花冤枉钱。算下来整个控制器只需要 4 个普通 GPIO 和微秒级延时，随便选一颗一两块钱的廉价单片机（比如自带 USB 从机的 CH552G，或者几毛钱的 CH32V003、STC8G1K08）配一颗几毛钱的 CH442E 模拟开关，三五块钱就能搞定整块小板；只有当你打算连电脑和模拟开关都省掉、让单片机发完握手后自己切换成 USB Host 独立读写 Flash 时，才真正用得上 ESP32-S3 这类带 USB OTG 主机外设的芯片。

杰理官方的第四代强制升级工具其实也预留了类似的入口，官方《工具拨码开关说明》里提到将第 7 位拨码拨上去即可开启电脑通信模式，收到电脑发来的升级指令后会自动执行相当于按下升级键的动作。不过官方并没有公开这套上位机触发指令的具体字节格式，而且也没法由脚本自由调节断电放电时长，想要彻底融入 Linux 自动化编译刷机流水线，还是自己用几块钱的便宜单片机搭一块可控下载器最省心。
